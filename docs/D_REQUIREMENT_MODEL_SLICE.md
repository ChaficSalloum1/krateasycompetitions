# D12 — requirement coverage across the competition

JOB: Show organisers the complete registered requirement inventory, why each item applies, the evidence for known values, and which requirements remain unresolved or outside this preview.
INPUT: Versioned field catalogue, current interpretation, exact draft compilation findings, source facts and revision.
OUTPUT: Versioned requirement report grouped by domain noun with dependency paths, ownership, lifecycle boundary, coverage state and evidence references; visible coverage map and requirement-driven questions.
AUTHORITATIVE OWNER: Interpretation owns questions. Compiler/validators own findings. Requirement report projects their evidence; it cannot certify Guard, draw, schedule or runtime.
INVARIANTS: Every registered draft field has exactly one domain assignment. Missing prerequisites are waiting, never falsely not applicable. Invalid or unsupported supplied values cannot appear complete. Unknown source clauses stay unresolved. No implicit second-cup bye policy. Reports bind revision and source; all later assurance scopes remain explicitly unchecked. No second engine.
TELEMETRY: Existing source/answer/review commands plus requirement-map inspection through structure_node_opened.
ACCEPTANCE SCENARIO: Omit every required field across knockout, round robin and pools-to-two-cups; introduce contradictions, unsupported values and structural invalidity; change prerequisites; inspect unknown text and future obligations. Known applicable requirements have source/default provenance, questions are not repeated after answers, and no supported draft can imply publish readiness.
NON-GOALS: Universal sport support, Phase E independent definition assurance, Phase F schedule interaction, Phase G repair, or runtime certification. Common nouns are extensible vocabulary, not evidence every sport works.
EXIT GATE: Requirement corpus, draft command suite and HTML-referenced UI checks pass. Current common/format/padel pack support and fixed compiler profile are explicit. Full D organiser/browser gate remains open.

Next F/G acceptance must cover visual court/time movement and division-wide breaks through candidate revisions, affected-scope/disruption evidence, independent collision/rest/dependency/window/lock checking and explicit approval. Rejected proposals leave the approved plan unchanged. K/L additionally protect played and in-progress truth. These user-requested controls are recorded in FUTURE.md until those gates admit implementation.

## State and ownership contract

| State | Cause | Allowed resolution |
|---|---|---|
| KNOWN | Applicable source fact or current organiser answer, no matching blocking finding | Edit creates a new report/revision; known does not mean independently assured |
| PROPOSED | Default, inheritance, automatic value or compiled fixed profile | Inspect and review current draft; unsupported edits cannot be assumed accepted |
| MISSING | Applicable required field absent and prerequisites settled | Answer or supply source evidence |
| WAITING | Applicability/value depends on missing, conflicting or invalid prerequisite | Resolve prerequisite; re-evaluate before asking dependent questions |
| CONFLICT | Unresolved source claims disagree | Explicit current-source decision or corrected source |
| UNSUPPORTED | Existing validator rejects registered semantics | Supported explicit replacement, or a separately admitted adapter; never silently downgrade |
| INVALID | Source, definition, roster, operation or graph finding blocks draft | Correct the implicated input; re-run existing checks |
| NOT_APPLICABLE | Known conditions exclude the rule | Re-evaluate when format or policy changes |
| UNRESOLVED | Uninterpreted source statement | Model supported wording or explicit context-only decision |
| NOT_EVALUATED | Lifecycle obligation has no evidence in this preview | Later independent assurance at its admitted gate; never local REVIEW |

The report is a pure revision-bound projection, not a new authoritative state machine. CreatorSession continues to own commands, stale-version rejection, idempotency and review invalidation. Requirement items bind source facts and existing finding codes; the report hash binds model/catalog versions, revision and interpretation. Vocabulary packs common/1, format/1 and padel-pairs/1 classify concepts; they do not establish other-sport implementation.

## Evidence and support boundary

117/117 creator tests: existing command/replay/roster/operations/locks plus 57 requirement cases. Fixed omission expectations cover three format families; unsupported sport/result/tie/format/qualification/comparison values, missing inherited second-cup byes, deferred prerequisites, invalid destination capacity, unknown text and non-promoting review are tested. Build and HTML-referenced bundled DOM interaction pass. Logs: phase-d-requirements-focused.txt and phase-d-requirements-ui.txt. No new full-core or real-browser QA claim.

The coverage inventory is complete for registered scalar draft fields and explicitly lists broader pending lifecycle obligations. It is not an exhaustive executable ontology for every sport or all padel rules. Named members, membership constraints, resource windows and locks retain their existing scoped editors and validators. Further sport policy and exception semantics still need supported rule contracts and counterexamples.
